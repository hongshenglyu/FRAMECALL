# 一年期项目路线图

本文档从 2026-05-20 开始，按“完整毕业设计工程 + 可验证实验项目”的节奏规划。目标不是赶出一个演示，而是在 2027 年毕业前形成结构完整、实验可信、工程可运行的足球裁判辅助争议事件分析系统。

## 1. 项目定位

本项目定位为“裁判辅助复核系统”，不是自动裁判系统。系统输出的是争议事件候选、证据指标、关键帧、轨迹和姿态线索，最终结论仍由裁判复核。

当前应坚持三条边界：

- `mock` 模式用于稳定工程闭环和演示，不冒充真实模型效果。
- `rule` 模式用于形成可解释候选逻辑，服务实验设计和论文分析。
- `real model` 模式逐步替换检测、跟踪和姿态模块，但每次替换都必须保留 fallback，不能破坏系统闭环。

## 2. 当前基线

截至 2026-05-20，项目已经完成：

- 三端闭环：Vue 前端、Spring Boot 后端、FastAPI AI 服务。
- 用户登录、视频上传、异步分析任务、事件入库、事件详情、裁判复核、手动补录、PDF 报告。
- 一键启动、停止、清理、闭环 smoke 脚本。
- AI 服务的可替换合同：检测、轨迹、犯规候选、局部姿态特征。
- `FOUL` 候选的第一版规则：最小距离、相对速度突变、闭合速度、局部姿态代理特征。
- 前端可解释证据面板和增强 PDF 报告。

按完整毕业设计口径，当前整体进度约为：

- 工程演示原型：`85%`
- 完整毕业设计系统：`40%`
- 真实 AI 与实验评估：`20%`

这个比例以后会以实验和真实模型进展为准，不再只按功能数量估计。

## 3. 里程碑路线

### 阶段 A：工程基线固化

时间：2026-05-20 至 2026-06-15

目标：把当前可跑系统整理成稳定基线。

任务：

- 梳理 API 合同和 AI 输出 JSON 合同。
- 明确 `mock`、`rule`、`real model` 三种模式的配置和回落行为。
- 补充后端、前端、AI 服务的最小自动化测试。
- 固化 smoke 验证，不让后续模型替换破坏闭环。
- 整理数据目录、模型目录、运行日志目录和清理策略。

验收标准：

- `run-system.ps1` 能稳定启动三端。
- `smoke-system.ps1` 能稳定通过。
- README、演示手册、API 文档、AI 合同文档互相一致。
- 新增功能必须能在 mock 模式下不依赖模型权重运行。

### 阶段 B：数据与标注体系

时间：2026-06-16 至 2026-08-15

目标：建立后续真实模型和论文实验需要的数据基础。

任务：

- 设计视频样本、事件片段、关键帧、轨迹、裁判复核标签的数据结构。
- 扩展标注管理页面，支持片段级事件标注和关键帧标注。
- 制定最小数据集规模，先做小样本闭环。
- 明确训练集、验证集、测试集划分规则。
- 给每个样本保存来源、时长、事件类型、标注人、标注版本。

验收标准：

- 至少有一批可复现实验的小规模标注数据。
- 标注格式可以被 AI 服务和实验脚本读取。
- 标注数据能导出为 JSON/CSV，供论文统计使用。

### 阶段 C：真实 YOLO 检测

时间：2026-08-16 至 2026-10-15

目标：把当前可选 YOLO 入口替换成可评估的真实检测模块。

任务：

- 准备球员、球、裁判类别的数据集。
- 选择 YOLO 小模型作为基线，必要时再比较中模型。
- 训练或微调检测模型。
- 将检测结果写入 `detections.json`，并在前端或报告中可视化。
- 统计 Precision、Recall、mAP50、FPS。

验收标准：

- 模型能在本机或目标演示环境稳定运行。
- 检测结果能被后续轨迹模块消费。
- 有可复现实验指标和推理耗时统计。

### 阶段 D：ByteTrack 轨迹关联

时间：2026-10-16 至 2026-11-30

目标：用真实多目标跟踪替换当前轨迹 adapter。

任务：

- 接入 ByteTrack 或等价跟踪实现。
- 统一 track id、时间戳、bbox、置信度输出格式。
- 输出 `tracks.json` 和轨迹预览图。
- 统计 IDF1、ID Switch、轨迹断裂情况。
- 将前端轨迹框展示接入真实轨迹。

验收标准：

- 同一个球员在短片段内能保持稳定 ID。
- 跟踪结果能驱动 `FOUL` 候选规则。
- 轨迹可视化和指标统计能复现。

### 阶段 E：犯规候选与局部姿态

时间：2026-12-01 至 2027-01-31

目标：把犯规候选从规则原型推进到可实验评估的候选召回模块。

任务：

- 基于真实轨迹重算距离、速度突变、接触窗口。
- 只对候选球员对做局部姿态估计，不全视频跑姿态。
- 比较不使用姿态、使用姿态代理、使用真实姿态模型的差异。
- 设计候选阈值和灵敏度策略。
- 统计 Recall、每 3 分钟误报数、关键帧定位误差。

验收标准：

- `FOUL` 候选能给出可解释证据链。
- 关键帧误差可被量化。
- 低误报和高召回两种模式能解释清楚。

### 阶段 F：手球与越位候选提示

时间：2027-02-01 至 2027-02-28

目标：把手球和越位保持为候选提示，不做最终判罚。

任务：

- 手球：球到上肢区域距离、球路变化、候选帧输出。
- 越位：球员位置、简化防线估计、场地标定可信度。
- 明确局限性，避免论文中宣称“自动判罚”。

验收标准：

- `HANDBALL` 和 `OFFSIDE` 有候选证据表。
- 证据可以被裁判复核页面和 PDF 报告展示。
- 论文中能解释为什么它们只是提示，不是最终判罚。

### 阶段 G：实验评估

时间：2027-03-01 至 2027-04-15

目标：形成论文最重要的实验结果。

任务：

- 检测实验：Precision、Recall、mAP、FPS。
- 跟踪实验：IDF1、ID Switch。
- 犯规候选实验：Recall、误报数、关键帧误差。
- 业务复核实验：裁判复核耗时、辅助前后一致率、主观信心。
- 生成图表和结果表，沉淀到论文材料中。

验收标准：

- 每组实验有数据来源、配置、指标和结论。
- 结果可复现，不只靠截图。
- 失败案例和局限性有记录。

### 阶段 H：论文与最终交付

时间：2027-04-16 至 2027-05-31

目标：把工程、算法、实验和论文合并成完整毕业设计。

任务：

- 固化最终演示数据和演示脚本。
- 整理项目部署文档和用户手册。
- 写论文系统设计、算法设计、实验评估、结论与展望。
- 准备答辩演示路线和备用方案。

验收标准：

- 项目可从干净环境按文档启动。
- 论文中的系统功能与实际系统一致。
- 演示、报告、实验数据三者口径一致。

## 4. 近期 Sprint

时间：2026-05-20 至 2026-06-05

本阶段不继续堆 AI 功能，先做质量整理。

优先任务：

- 新增 AI 输出合同文档，定义 `analysis_result.json`、`detections.json`、`tracks.json`、`foul_candidates.json`、`pose_features.json`。
- 给 AI 服务增加最小单元测试，覆盖 mock、YOLO fallback、tracking fallback、foul rule、pose rule。
- 给后端增加接口级 smoke 或集成测试，至少覆盖登录、任务详情、事件详情、报告导出。
- 检查前端核心页面在 1440px 和 1280px 下的布局。
- 明确数据标注格式，为下一阶段数据体系做准备。

完成标准：

- 本 sprint 后任何模型替换都不能绕过 JSON 合同。
- 所有新增模块必须能在无模型权重环境下通过 smoke。
- 文档能让未来的自己快速判断“这个文件属于 mock、rule 还是真实模型”。

## 5. 长期质量原则

- 每一个 AI 模块先定义输入输出合同，再接模型。
- 每一次真实模型替换都保留 fallback。
- 每一个实验指标都要能追溯到数据、配置和代码版本。
- 前端展示、PDF 报告、论文表述必须使用同一套证据口径。
- 不为了短期演示把最终判罚责任交给模型。

## 6. 暂不做的事

- 不宣称系统能自动判罚最终结果。
- 不急着写论文正文。
- 不在没有标注数据的情况下追求复杂模型。
- 不全视频跑姿态估计，姿态只服务候选球员对。
- 不把手球和越位做成最终判罚，只保留候选提示。
